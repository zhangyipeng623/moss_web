Agent 记忆系统优化

检索评分公式重构 + 时间衰减引入  |  基于认知科学 Ebbinghaus 遗忘曲线  |  日期：2026-05-17  |  分支：feat/recsys

概述

MOSS Agent 的记忆系统采用短期记忆（ShortTermMemory）+ 事件记忆（EventMemory）双层架构， 核心设计理念是模拟真实用户的记忆模式：短期记忆保留近 3 轮的浏览片段（模拟刷信息流的瞬时记忆）， 事件记忆存储 Agent 自主选择的重要信息（模拟人类选择性长期记忆）。

在记忆检索环节，select_relevant_events 方法负责从 EventMemory 中选取与当前 Feed 上下文最相关的事件， 注入 LLM 决策的 prompt 中。然而，当前检索评分公式存在结构性缺陷——规则加分权重过大，可轻易压倒 Agent 自身的重要性判断。

本次优化不改架构、不上向量检索、不增加计算耗时。仅重构评分公式并引入时间衰减机制。

1. 当前记忆系统架构

1.1 记忆四组件

组件类型容量核心功能
StaticContext 静态上下文 固定 Agent 画像文本 + 全局事件描述，整个模拟过程中不变
ShortTermMemory 短期记忆（滑动窗口） 最近 3 轮 每轮保留 Feed 快照 + 执行动作 + 输出摘要。模拟浏览信息流时的瞬时记忆
AgentState 心理状态 单条 情绪/强度/当前目标/关注话题/立场摘要/重点关注对象。LLM 每轮更新
EventMemory 事件记忆（持久化） 最多 50 条 Agent 自主选择存储的重要事件摘要。按 importance 排序，超出上限淘汰低重要性记录

四组件在决策循环中的流转：

  1. 检索阶段：从 EventMemory 中select_relevant_events 选出与当前 Feed 最相关的 top-5 事件
  2. 构建 prompt：拼接静态画像 + 短期记忆 + AgentState + 相关事件 + 当前环境快照
  3. LLM 决策：Agent 执行工具调用（发帖/评论/点赞/转发/不动），输出状态更新和事件记忆更新
  4. 更新记忆：MemoryManager 写入新的 ShortTermRecord，若 Agent 判定 should_store 则写入 EventMemory

1.2 设计哲学

记忆系统的设计遵循两个核心认知原则：

  • 工作记忆有限：真实用户在刷社交平台时，不会记住 10 分钟前看到的每一条帖子。3 轮短期记忆窗口模拟了这种"看完就忘"的浏览特征。
  • 选择性编码：不是所有信息都值得长期记忆。Agent 自己决定什么事件足够重要去记住（should_store=true），并由 Agent 自己评定重要性分数。这模拟了人类"只记住想记住的"这一特征。
设计者原话："我们模拟的是用户，是一个人。他在浏览社交平台的时候，记忆也不是实时记住所有事情的。短期的 3 轮用来模拟查看社交平台时只会记住短暂浏览片段；长期的 EventMemory 用来记住我们想记住的重要信息。"

2. 问题诊断：检索评分的结构性缺陷

2.1 当前评分公式

def select_relevant_events(snapshot, top_k=5): for record in event_memory.records: score = record.importance # 基础分：Agent 自评重要性 (0~1) if 帖子ID匹配当前Feed: score += 1.0 # ← 直接加 1 if 作者在Feed中: score += 0.7 if 话题词在Feed文本中: score += 0.5 if 话题匹配关注主题: score += 0.3 if 关注对象匹配: score += 0.2 # 规则加分总额可达 +2.7，而 importance 仅 0~1

核心问题：规则加分权重过大，可以轻易压倒 Agent 自身的重要性判断。

2.2 缺陷示例

场景旧公式得分问题
Agent 评为 importance=0.9 的重要事件，当前 Feed 无直接匹配 0.9 基准线
Agent 评为 importance=0.3 的次要事件，但帖子 ID + 作者 + 话题全部匹配 2.5（反超！） 一个 Agent 自己都认为不重要的事件，仅因为规则匹配就排到了最前面
importance=0.9 事件，全匹配 3.1 与 0.3 事件的差距 (3.1 vs 2.5) 被压缩到仅 0.6
根本矛盾：Agent 当初自主判断"这个事件的重要度是 0.3"，但在检索时，系统通过规则匹配强行将其推到 2.5 分。 这等于否定了 Agent 自己的判断——既然检索时规则匹配说了算，那 Agent 当初评分还有什么意义？

2.3 附加问题：缺乏时间衰减

当前检索完全忽略事件的存储时间。第 1 轮存入的事件和第 50 轮存入的事件在检索时完全平等。 这不符合人类记忆规律——现实中，时间越久远的记忆越难以被当前刺激所触发。

在长周期模拟（如 50+ 轮）中，EventMemory 会被早期事件占满，而这些"远古记忆"的新鲜度与近期事件完全相同， 导致检索结果与当前情境脱节。

3. 优化方案：乘法评分 + 时间衰减

3.1 新评分公式

score = importance × recency_decay × (1 + context_boost) 其中： importance = Agent 当初自评的重要性 (0~1)，主信号 recency_decay = exp(-λ × rounds_ago)，Ebbinghaus 遗忘曲线 context_boost = 各项匹配累加，硬上限 0.3

三项因子的设计逻辑：

因子公式作用为什么这样设计
importance Agent 原始评分 0~1 主信号 尊重 Agent 的自主判断。这是乘法的基础项，为 0 则结果恒为 0
recency_decay exp(-0.07 × rounds_ago) 时间衰减，半衰期 ~10 轮 符合 Ebbinghaus 遗忘曲线。近期记忆更易被触发，远古记忆自然淡出
1 + context_boost 加成上限 0.3（即乘数 ≤ 1.3） 锦上添花 上下文联想提供合理增益，但硬上限确保规则匹配永远不能主导排序

3.2 context_boost 细则

匹配条件加成值认知依据
相关用户出现在当前 Feed 中 +0.12 看到某个人会触发与此人相关记忆，这是最自然的记忆触发机制
话题匹配 Agent 当前关注主题 +0.10 正在关注的话题是记忆检索的高优先级线索
帖子 ID 出现在当前 Feed（引用/转发） +0.05 看到同一帖子被二次传播，提醒此前与此帖的交互
话题词在 Feed 文本中出现 +0.03 弱信号：Feed 中提到类似话题，提供轻微联想

四项累加上限为 0.30。如果全匹配（0.12+0.10+0.05+0.03=0.30），乘数为 1.30，即最多提升 30%。

去除了"关注对象匹配"（+0.20）：此项与"相关用户匹配"高度重叠且无认知科学依据。

3.3 时间衰减参数

衰减系数 λ 默认取 0.07，对应半衰期约 10 轮。 这意味着：一条重要性评分相同的记忆，在 10 轮后其检索得分将降至原始的一半（在无上下文加成的情况下）。

λ半衰期适用场景
0.05~14 轮慢节奏长周期模拟，Agent 需要在较长时间内保持记忆可及性
0.07（推荐）~10 轮均衡选择，大多数场景适用
0.10~7 轮快节奏短周期模拟，记忆快速更替

λ 写入 calibration_profile.yaml 的 simulation.memory.decay_lambda 字段，可针对不同实验场景调整。

3.4 为什么不在淘汰（Eviction）中加时间衰减

EventMemory 的淘汰策略保持纯 importance 排序。理由：

  • 语义一致性：淘汰 = "忘记"，而 Agent 当初评了高 importance 的事件就是"不想忘记的"。如果因为时间久远就淘汰高重要性事件，等于系统替 Agent 做了"这个不再重要"的判断，与"Agent 自主选择记忆"的设计哲学矛盾。
  • 检索已足够：时间衰减在检索阶段生效即可。一条远古高重要性事件在检索时得分会被自然压低，但仍保留在记忆中——这模拟了"我记得但不太想得起来"的状态。
  • 低风险：即便远古高重要性事件偶尔被触发，也不会造成行为异常——它不过是 prompt 中的一条相关上下文。

4. 方案对比与效果预估

4.1 旧 vs 新 对比

旧方案 加法评分

score = importance + 1.0 × 帖子ID匹配 + 0.7 × 作者匹配 + 0.5 × 话题文本匹配 + 0.3 × 关注主题匹配 + 0.2 × 关注对象匹配
  • 重要性权重被稀释
  • 规则匹配可主导排序
  • 无时间维度

新方案 乘法评分 + 时间衰减

score = importance × exp(-λ × rounds_ago) × (1 + min(context_boost, 0.3))
  • 重要性为主导信号
  • 规则匹配仅提供有限增益
  • 时间自然衰减

4.2 关键场景得分对比

场景旧公式新公式判断
importance=0.9，无匹配，本轮 0.90 0.90 一致
importance=0.3，全匹配，本轮 2.50 0.39 修复 不再反超
importance=0.9，全匹配，本轮 3.10 1.17 合理 高重要性+高匹配自然得高分
importance=0.9，无匹配，20轮前 0.90 0.22 改进 远古记忆自然淡出
importance=0.6，作者匹配，5轮前 1.30 0.53 合理 中等重要性+中等匹配

6.2 不采用向量检索的合理性

2025–2026 行业最佳实践中，向量检索被广泛推荐用于语义相似记忆的发现。 但本方案有意不采用，理由如下：

  • 性能约束：向量检索（embedding + similarity search）在 50 条记录的规模下，计算开销远超当前的 O(n) 线性扫描。每轮决策循环的时间预算有限。
  • 话题空间集中：本系统模拟的场景（如美伊冲突）话题空间相对集中，字符串匹配的精度足以覆盖大多数检索需求。
  • Agent 自主判断已提供语义信号：importance 评分本身就是 Agent 对事件"语义重要性"的综合判断。与其用 embedding 做语义相似度，不如信任 Agent 自己的评分。
设计取舍：当记录量增长到数百条以上且话题空间显著发散时，可考虑引入轻量级向量检索（如用 SentenceTransformer 对 summary 做嵌入，用内积做相似度排序）。但这属于远期优化方向，当前规模下不需要。
